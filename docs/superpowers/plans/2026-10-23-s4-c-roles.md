# S4 stage C: role rules (T-TEN-07, T-TEN-05, T-AUTH-04) — Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Enforce the three role rules of spec decision 5 and prove them under real token verification:
- owner-only management of admins and owners (T-TEN-07);
- org admin on every destructive org-scoped route (T-TEN-05);
- a verified email for first sign-in and for invite acceptance (T-AUTH-04).

**Architecture:**
- **T-TEN-05:** a new sync helper `check_org_role(current_user, minimum_role)` in `dependencies.py` reads the **legacy** store (`users.org_role`, global-admin bypass), the same store as `check_org_access` / `_ensure_org_access`. Each of the 7 destructive routes that only check membership today calls it right after its org check. `route_table.py` gets `min_role="org:admin"` on those 7.
- **T-TEN-07:** `members.py` reads the **Membership** store it already uses (`require_membership_role("admin")` stays the route gate). One helper, `_require_owner(membership)`, is called wherever the action touches an admin or an owner.
- **T-AUTH-04:** token verification moves out of `get_current_user` into a new dependency `get_token_claims`. `get_current_user` depends on it, and `accept_invite` also depends on it to read `email_verified`. FastAPI caches a dependency per request, so the token is verified once.
- **Tests:** under real verification, in `backend/tests/authz/tenancy/`, on stage B's fixture world. A role-floor sweep is driven by `route_table.ROUTES[key].min_role` and stage B's `CASES`; a T-TEN-07 matrix and the T-AUTH-04 tests get their own files.

**Tech Stack:** Python 3.11, FastAPI 0.133, SQLAlchemy async + Postgres 15, pytest 9 + pytest-asyncio, httpx `ASGITransport`, firebase-admin 6.4.0 (real verification via stage A). Frontend: React + Vite, Vitest, eslint (`--max-warnings 0`), Firebase JS SDK.

**Spec:** `docs/superpowers/specs/2026-10-22-s4-authorization-assurance-design.md`: decision 5 in full; decision 4's role-store rule (L108); Anti-goals; Constraints; the stage C row.

## Review Focus

1. **The role check runs before the org check**, so a B member is refused with "Insufficient organization role" instead of "Access denied", and a future org-check regression hides behind the role gate. Pinned by the order rule in Task 1 Step 3 and by stage B's `test_cross_tenant_denied` (B's owner, who passes every role gate, must still get `case.denial_detail`).
2. **The new legacy check drops the global-admin bypass**, which would quietly break the documented S3 boundary. Pinned by stage B's `test_global_admin_boundary` (unchanged) and by `test_global_admin_passes_role_floor` (Task 1).
3. **An admin edits itself.** Self-demotion and self-removal of an admin are actions on an admin, so they become owner-only. Pinned in Task 2's matrix (`admin_self_demote`, `admin_self_remove`, both 403), and recorded in the PR body as intended.
4. **A user whose row predates T-AUTH-04 is locked out.** The rule covers only auto-create and invite acceptance; an existing bound user with an unverified token must still sign in. Pinned by `test_existing_user_unverified_still_signs_in` (Task 3).
5. **A verified token for a different address than the account's.** `email_verified` vouches only for the token's own email, while the invite match uses the stored row's email. Pinned by `test_accept_invite_refused_when_token_email_differs` (Task 3).
6. **The `email_verified` claim is missing or not a boolean** (`None`, `"true"`). Only literal `True` passes, matching the S0 link path's `is not True`. Pinned by `test_auto_create_refused_when_claim_missing` and `test_auto_create_refused_when_claim_is_string` (Task 3).

## Decisions made in this plan

- **The destructive list (T-TEN-05)**, derived from `route_table.py` by the spec rule (delete org data, disconnect an integration, revoke an org credential, delete or export the org):

  | Route | Today | Stage C |
  |---|---|---|
  | `DELETE /organizations/{org_id}/vendors/{vendor_id}` | member | **org admin** (legacy) |
  | `DELETE /organizations/{org_id}/uploads/{upload_id}` | member | **org admin** (legacy) |
  | `DELETE /organizations/{org_id}/domains/{domain_id}` | member | **org admin** (legacy) |
  | `POST /organizations/{org_id}/scan-runs/{scan_run_id}/rollback` (deletes the run's assets) | member | **org admin** (legacy) |
  | `DELETE /assessments/{assessment_id}` | member | **org admin** (legacy) |
  | `DELETE /integrations/m365` (disconnect) | member | **org admin** (legacy) |
  | `POST /integrations/m365/consent` (its callback replaces the org's stored credential and tenant, so it disconnects the current connection) | member | **org admin** (legacy) |
  | `DELETE /agents/{agent_id}`, `POST /agents/{agent_id}/rotate` (revokes the predecessor after grace) | org admin (legacy) | unchanged |
  | `DELETE /{organizations,orgs}/{org_id}/invites/{invite_id}` (2 aliases) | org admin (Membership) | unchanged |
  | `DELETE /{organizations,orgs}/{org_id}/members/{user_id}` (2 aliases) | org admin (Membership) | unchanged; T-TEN-07 adds owner-only targets |
  | `DELETE /organizations/{org_id}`, `GET .../export`, `POST .../retention/run` | global admin (`administrator` class) | unchanged; stricter than org admin |

  **Not destructive** (stay member, by the spec's "creating and editing"): vendor and inventory CSV import (they add rows), `PUT .../assets/{id}/tags` (replaces one asset's tags), the two finding-status `PATCH`es, upload download, M365 sync (it adds or updates assets from the connected tenant).
- **Revoking a pending admin invite stays admin-level** (the builder's call, recorded). Revoking removes a pending grant instead of making one, the owner can re-issue it, and admins already list every invite. Making it owner-only would add a role branch for no reduction in privilege.
- **Owner-only denials** return **403** `"Owner role required"`. The existing 400s stay as they are: `"Cannot invite as owner"`, `"Cannot assign owner role through this endpoint"`, and the last-owner messages. The owner-only check runs after the 404 member lookup and before the last-owner checks, so an admin acting on the last owner gets 403, not 400.
- **T-AUTH-04 refusals** return **403** `"Email address not verified"` on both paths. That's distinct from the S0 link-path detail (`"Unable to link this sign-in to an existing account"`) so the frontend can show a specific message. In `accept_invite` the check runs first, before the invite lookup, so nothing is read or written. It also requires the token's verified address to equal the account's stored address, because the invite match reads the stored address. That refusal is a separate 403, `"Signed-in email does not match this account"`, so the frontend doesn't offer a verify loop that can never succeed.
- **Role tests get their own table, not new `Case` fields.** The rule is per route and lives in `route_table.ROUTES[key].min_role`; the request comes from stage B's `CASES[key].build`. A new `Case` field would duplicate `min_role`. The `b_member` rule in `test_cross_tenant.py` already keys on `min_role == "org:admin"`; all 7 changed routes are path routes in `_DENIED`, where `b_member` only needs `{403, 404}`, so it stays correct unchanged. Its `{403, 404}` doesn't pin the check order, so Task 1 adds `test_other_org_member_hits_org_check_first`.
- **The assessments 500 stays pinned.** `DELETE /assessments/{id}` still returns 500 for an allowed caller (todos, "S4 stage B"). The role-floor test proves an admin passes the role check by getting `case.allowed` (500) with `case.allowed_detail` ("Failed to delete assessment"), which is raised only after the role check; a member gets 403 first.
- **`[K]` = 18:** 1 (analytics, stage B) + 7 destructive routes + 8 member routes (`POST` invites ×2, `PUT`/`PATCH` members ×4, `DELETE` members ×2) + 2 T-AUTH-04 paths (auto-create in `get_current_user`, `POST /invites/{token}/accept`). Revoke-invite isn't counted: its behaviour doesn't change.
